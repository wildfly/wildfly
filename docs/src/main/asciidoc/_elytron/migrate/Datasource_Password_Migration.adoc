[[Datasource_Password_Migration]]
= Datasource Passwords

ifdef::env-github[]
:tip-caption: :bulb:
:note-caption: :information_source:
:important-caption: :heavy_exclamation_mark:
:caution-caption: :fire:
:warning-caption: :warning:
endif::[]

This section describes how to migrate datasources that obtain their database password from
one of the PicketBox login modules that older documentation recommends for "encrypting"
datasource passwords, namely `SecureIdentityLoginModule` and
`JaasSecurityDomainIdentityLoginModule` used together with the `PBEUtils` command line
tool.

[WARNING]
====
Neither of these login modules provides meaningful protection for the password and both
of them should be considered a way of obfuscating, not of encrypting, the password:

* `org.jboss.resource.security.SecureIdentityLoginModule` encrypts the password with a key
that is hard coded in the login module. The login module is open source, so the clear text
password can be recovered by anyone who is able to read the configuration file.
* `org.picketbox.datasource.security.JaasSecurityDomainIdentityLoginModule` combined with
`org.picketbox.datasource.security.PBEUtils` uses password based encryption whose
passphrase, salt and iteration count have to be stored in the configuration next to the
encrypted value, and it relies on legacy algorithms that no longer provide adequate
protection.

Both login modules are part of the legacy `security` subsystem, which is not supported in
WildFly. A datasource that references a legacy security domain through the
`security-domain` or `recovery-security-domain` attribute is rejected with
`WFLYJCA0124: Datasource <name> is configured to require the legacy security subsystem,
which is not present`, and a `-ds.xml` deployment that uses them fails to parse with
`WFLYJCA0132: Legacy security is no longer supported. Please use Elytron configuration
instead`.
====

[[picketbox-secure-identity-login-module]]
== PicketBox SecureIdentityLoginModule

A legacy configuration encrypting a datasource password typically looks like the
following. The password was generated with the `main` method of the login module and the
datasource referenced the resulting security domain.

[source,xml,options="nowrap"]
----
        <subsystem xmlns="urn:jboss:domain:security:2.0">
            <security-domains>
                ...
                <security-domain name="encrypted-ds">
                    <authentication>
                        <login-module code="org.jboss.resource.security.SecureIdentityLoginModule" flag="required">
                            <module-option name="username" value="sa"/>
                            <module-option name="password" value="5dfc52b51bd35553df8592078de921bc"/>
                        </login-module>
                    </authentication>
                </security-domain>
            </security-domains>
        </subsystem>

        <subsystem xmlns="urn:jboss:domain:datasources:7.2">
            <datasources>
                <datasource jndi-name="java:jboss/datasources/ExampleDS" pool-name="ExampleDS">
                    <connection-url>jdbc:h2:mem:test;DB_CLOSE_DELAY=-1</connection-url>
                    <driver>h2</driver>
                    <security>
                        <security-domain>encrypted-ds</security-domain>
                    </security>
                </datasource>
            </datasources>
        </subsystem>
----

The `JaasSecurityDomainIdentityLoginModule` variant is equivalent, except that the
`login-module` code is
`org.picketbox.datasource.security.JaasSecurityDomainIdentityLoginModule`, the encrypted
password was produced by `PBEUtils`, and an additional `jaasSecurityDomain` module option
points at a `jboss:jaas-security-domain` holding the keystore used for the encryption.

[[elytron-credential-store]]
== Elytron Credential Store

The equivalent Elytron configuration stores the password in a credential store and
references it from the datasource. The credential store is encrypted with a password that
you choose, and the password itself is never written to the configuration files.

The migration needs the clear text database password. If it is no longer known, obtain it
from the database administrator, or reset it, before starting; as explained above, values
encrypted by either login module are recoverable, so they do not have to be treated as
lost.

Create a credential store and add the database password to it:

[source,options="nowrap"]
----
./subsystem=elytron/credential-store=mycredstore:add( \
    path=mycredstore.cs, \
    relative-to=jboss.server.config.dir, \
    credential-reference={clear-text=StorePassword}, \
    create=true)

history --disable
./subsystem=elytron/credential-store=mycredstore:add-alias(alias=example-ds, secret-value=sa)
history --enable
----

[NOTE]

The CLI history is temporarily disabled so that the clear text password is not written to
the CLI history file.

Then remove the legacy security domain reference from the datasource, replace it with the
user name and a `credential-reference`, and reload the server:

[source,options="nowrap"]
----
./subsystem=datasources/data-source=ExampleDS:undefine-attribute(name=security-domain)
./subsystem=datasources/data-source=ExampleDS:write-attribute(name=user-name, value=sa)
./subsystem=datasources/data-source=ExampleDS:write-attribute(name=credential-reference, \
    value={store=mycredstore, alias=example-ds})
reload
----

This results in a `credential-store` resource in the `elytron` subsystem and the following
datasource configuration, which no longer contains any password:

[source,xml,options="nowrap"]
----
        <subsystem xmlns="urn:jboss:domain:datasources:7.2">
            <datasources>
                <datasource jndi-name="java:jboss/datasources/ExampleDS" pool-name="ExampleDS">
                    <connection-url>jdbc:h2:mem:test;DB_CLOSE_DELAY=-1</connection-url>
                    <driver>h2</driver>
                    <security user-name="sa">
                        <credential-reference store="mycredstore" alias="example-ds"/>
                    </security>
                </datasource>
            </datasources>
        </subsystem>
----

An XA datasource that used `recovery-security-domain` for its recovery identity is
migrated the same way, using the `recovery-username` and `recovery-credential-reference`
attributes.

[[elytron-authentication-context]]
== Elytron Authentication Context

If the legacy security domain was used to distinguish connections in the pool rather than
to hide a single static password, migrate it to an Elytron `authentication-context`
instead. The `authentication-context` attribute is an alternative to `user-name`, so any
existing user name has to be undefined first.

[source,options="nowrap"]
----
./subsystem=elytron/authentication-configuration=ds-auth:add( \
    authentication-name=sa, \
    credential-reference={store=mycredstore, alias=example-ds})
./subsystem=elytron/authentication-context=ds-context:add( \
    match-rules=[{authentication-configuration=ds-auth}])

./subsystem=datasources/data-source=ExampleDS:undefine-attribute(name=security-domain)
./subsystem=datasources/data-source=ExampleDS:undefine-attribute(name=password)
./subsystem=datasources/data-source=ExampleDS:undefine-attribute(name=user-name)
./subsystem=datasources/data-source=ExampleDS:write-attribute(name=elytron-enabled, value=true)
./subsystem=datasources/data-source=ExampleDS:write-attribute(name=authentication-context, value=ds-context)
reload
----

[IMPORTANT]

`authentication-context` is only taken into account when `elytron-enabled` is set to
`true` on the same datasource. Although `elytron-enabled` is deprecated, it still defaults
to `false`, and a datasource that sets `authentication-context` without it is rejected
because the value is treated as the name of a legacy security domain.

An XA datasource uses `recovery-elytron-enabled` and `recovery-authentication-context` for
the recovery identity.

[[further-reading]]
== Further Reading

Resource adapter connection definitions that referenced the same legacy security domains
are migrated in the same way, using the `authentication-context`,
`recovery-authentication-context` and `recovery-credential-reference` attributes of the
`connection-definition` resource.

See <<CredentialStore,Credential Store>> for the full set of credential store options and
<<EncryptedExpressions,Encrypted Expressions>> if the value has to stay in the
configuration file. The
<<Migration_Guide.adoc#Migration_PicketBox_Vault,PicketBox Vault>> section of the WildFly
Migration Guide covers converting an existing vault to a credential store.
