# Subsystem review checklist

Use this for a diff that changes a subsystem management contract or its XML. Apply only the checks the diff triggers; an internal implementation fix with no model or XML change needs behavior tests, not a versioning review. For changes targeting 43.0.0.Final, 42.0.0.Final remains the baseline even after 43.0.0.Beta1; apply this preceding-Final rule independently to model and XML versions. Use the [development guide](subsystem-development.md) and the affected subsystem's pattern for details.

- [ ] **Identify the contract change.** Trace the registered attribute, child resource, operation, default, validator, capability, description, or runtime-only/persistent behavior through its handlers. Check add and write paths separately where applicable.
- [ ] **Check the model version.** Compare the current version with the applicable preceding-Final baseline and identify supported older model targets. If the version has already changed since that baseline, no further bump is needed. Otherwise assess whether this change needs one. Report uncertainty only if the applicable baseline cannot be established.
- [ ] **Assess each older model target.** Inspect the actual transformer path, including operation and resource transformation where relevant. Discard only an undefined or behaviorally equivalent value; convert when meaning survives; reject incompatible defined values, resources, or operations. If transformer registration changes, verify it is discoverable through a service entry or `@MetaInfServices`. Record evidence when no transformer change is needed.
- [ ] **Check XML separately when syntax or persistence changes.** Find the active reader and writer. Compare the XML namespace/schema version with the applicable preceding-Final baseline independently of the model version; no further bump is needed if it already changed since that baseline. Report uncertainty only if the applicable baseline cannot be established. Gate new syntax away from published old namespaces. Update and validate the matching XSD if this subsystem uses XSDs.
- [ ] **Check focused evidence.** Look for current and old XML parse/round-trip tests, model and runtime behavior tests, successful transformation tests, and rejection tests for incompatible cases. Check descriptions, feature stability, default configuration, and feature-pack metadata only where the diff affects them. Confirm the relevant tests actually ran.

**Review finding:** If an applicable step is missing or unsupported, comment at the affected code. Name the older model or XML form at risk, explain the failure or silent behavior change, and ask for the missing change and test or evidence that the existing contract covers it. Do not approve a compatibility-sensitive change solely because tests pass.
